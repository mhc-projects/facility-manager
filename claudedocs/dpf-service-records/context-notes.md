# 컨텍스트 노트 — DPF 서비스 이력(AS/크리닝/물류) (2026-09-11)

## 배경
DPF 담당자들이 익숙해하는 크린어스(제조사) DEAR System의 부착현황/물류관리/접수현황 화면 구조를 로그인해서 직접 조사하고,
facility-manager `/dpf` 모듈에 이식할 설계를 작성함. 전체 설계는 `../dpf-as-logistics-design.md` 참고.

## 핵심 결정 (사용자 확정)
- 본사/협력사 접수경로 구분 없음 — 블루온은 콜센터가 전화 전부 직접 받음.
- 크린어스는 vendor enum에 지금 추가 안 함 (fujino/mz 유지).
- 첨부파일(12슬롯) 구조는 1단계에서 만들지 않음 — 담당자 요구 구체화되면 5단계로.
- 연장 워크플로우는 전자결재 미연동, 단순 boolean 필드.
- 회차(round_no)는 전환(크리닝↔AS) 시 새 category 기준 재채번, 원래 분류는 `converted_from_category`에만 흔적.
- 변경정보 오버레이는 `dpf_vehicles`에 컬럼 추가 방식(파생 계산 아님) — 부착현황 목록에서 조인 없이 보여주기 위함.

## 어드바이저 검토에서 나온 수정 (2026-09-11, 구현 전)
1차 설계안을 어드바이저에게 검토받아 6개 필수 수정 + 5개 권장 수정을 반영함 (설계 문서 각 절에 타임스탬프로 표시돼 있음).
- **round_no 채번을 API가 아니라 DB 트리거로**: Supabase JS 호출에서 "MAX 조회→+1→INSERT"를 하면 동시 접수 시 경쟁 상태 발생.
  전자결재 approve/submit 라우트가 `lib/supabase-direct`의 `transaction()` 헬퍼를 빠뜨려 부분 업데이트 버그가 났던 전례가 있어서
  ([[project_approval_pending_fixes]] 참고), API 코드가 매번 기억해야 하는 방식 대신 DB 트리거로 강제함.
- **오버레이 write-back 대상 재정리**: 1차 초안은 `current_vin_override`까지 자동 write-back한다고 적었지만, 접수 등록 폼에
  차량번호/차대번호 입력란이 아예 없어서(§2.2 관찰 내용에 없음) 자동화할 소스가 없었음. `current_plate_number`/`current_vin_override`/
  `is_special_management`/`is_special_sale`은 전부 수동 전용(VehicleFormModal), 연락처·출동지역만 자동 write-back으로 수정.
- **처리내용(processing_content) 컬럼 누락 발견** — 내역 테이블의 3번째 텍스트 필드가 스키마에 빠져 있었음. 추가.
- **삭제≠취소**: 협회청구일자를 들고 있는 원장을 하드 삭제하면 안 됨. `is_deleted` 소프트 삭제 + `status`에 `cancelled` 추가.
- **지자체/처리점은 자유 텍스트**: 크린어스의 코드 테이블(지자체 168개 등)은 우리 쪽에 없음. `local_gov_code`/`service_branch_id`를
  `local_government`/`service_branch` 자유 텍스트로 변경. 담당AS기사/처리기사도 1단계는 자유 텍스트, employees FK 연동은 후속 과제.
- **특판(is_special_sale)은 차량 속성**: 크린어스 필터에서 특판은 접수 건이 아니라 계약(차량) 단위 속성이었음 — `dpf_vehicles`로 이동.
- **1단계 API 라우트를 vin 스코프 서브레코드 패턴으로**: 처음엔 `/api/dpf/service-records` 최상위 엔드포인트를 1단계에 넣었는데,
  기존 `installations`/`inspections` 라우트와 패턴을 맞추는 게 맞음 — 최상위 통합 리스트 엔드포인트는 2단계(접수현황 페이지)로 이동.

## 미관찰 (구현 시 주의)
- 크린어스 "서류 보기" 상세 화면 — 클릭이 반응하지 않아 구조를 못 봄. 첨부파일 설계(§4.7)는 등록 폼의 파일 슬롯에서 유추한 것.
- 크린어스 "접수종류" 드롭다운 옵션 — 클릭 위치가 빗나가서 못 엶. 1단계에서는 `category` 자체를 접수종류로 취급.

## 2단계 구현 중 발견 (2026-09-11)
- **`.or()` 조인 필터 문법**: PostgREST의 `or=()` 구문은 와일드카드로 `%`가 아니라 `*`를 쓴다. `%`를 그대로 넣으면
  "failed to parse logic tree" 파싱 에러가 남(문서화되지 않아 실제 요청으로 확인). 임베디드 테이블(조인) 필터는 문자열에
  `테이블명.컬럼명` 접두어를 직접 넣는 대신 supabase-js의 `.or(filter, { foreignTable: '...' })` 2번째 인자를 쓰는 게 맞음.
  실제 요청(`?q=8787`, `?q=이채규`)으로 검증 완료.
- **dev 서버 청크 캐싱이 클라이언트 네비게이션 테스트를 오도할 수 있다**: `?tab=` 기능을 클라이언트 사이드 Link 클릭으로 테스트했을 때
  반복적으로 실패해서 useEffect까지 추가하며 원인을 찾았는데, 실제로는 로직이 처음부터 정상이었고 **같은 브라우저 탭에서 파일을
  수정하는 동안 이미 로드돼 있던 `/dpf/[vin]` 페이지의 JS 청크를 클라이언트 사이드 네비게이션이 재사용**해서 최신 코드가
  반영 안 되고 있었던 것. `navigate`(주소창 이동)로 시작 페이지를 하드 리로드해서 청크를 최신화한 뒤 그 상태에서 클릭 네비게이션을
  하면 정상 동작함을 확인. **[[feedback_local_test_hard_reload]]가 "dev 서버 재시작 후"만 언급하는데, 실제로는 서버 재시작 없이
  파일만 수정해도 같은 탭에서 클라이언트 사이드 네비게이션을 반복 테스트하면 같은 증상이 난다** — 이 메모리를 갱신할 가치가 있음.
  결과적으로 유지한 것: `useEffect`로 `searchParams` 변경 시 `activeTab`을 보정하는 로직(실사용자 시나리오에서도 Next.js
  라우터 캐시로 컴포넌트가 재사용되는 경우의 안전망으로 의미가 있어 남김), 디버그용 `data-debug-*` 속성은 제거함.

## 2단계 사후 검토 (2026-09-11, 어드바이저)
2단계 결과물 어드바이저 재검토 — "clean, 체크리스트 전부 실제 브라우저 증거로 검증됨, 커밋 분리도 정확함" 확인. 잔여 3건(블로커 아님):
1. 정리 SQL이 1단계 시점 기준이라 2단계 검증분까지 포함하는지 재확인 필요하다는 지적 — 확인 결과 2단계 검증은 1단계에서 만든
   레코드를 재사용했을 뿐 추가로 쓴 필드가 없어(무선 연락처만 입력) 기존 2줄 SQL로 충분함. 사용자가 2026-09-11 실행 완료.
2. `app/dpf/service/page.tsx`의 통계 재조회 `useEffect`가 `[result.total]`에 걸려 있어 필터 바뀔 때마다(=목록 건수가 바뀔 때마다)
   전역 통계를 다시 조회함 — 지금 규모에선 무해하지만 의미상 필터(로컬)와 통계(전역)를 섞은 것. 3단계에서 이 페이지에 등록 버튼이
   생기면 "마운트 시 1회 + 등록 성공 시에만" 재조회로 좁히는 걸 검토. 2단계 결함은 아니라 지금은 고치지 않음.
3. `initialTab`과 보정용 `useEffect`가 같이 있는 이유를 주석으로 남겨둠(page.tsx:62,71) — 둘 다 필요(초기 렌더 vs 라우터 캐시 재사용)함을
   다음 세션이 실수로 하나를 지우지 않도록 명시.

## 3단계 계획 (2026-09-11, 어드바이저 3차 검토로 구체화)
- **성능**: `/dpf` 목록에 크리닝횟수/AS횟수 등을 파생 컬럼으로 붙이는 게 "조회 레이어 추가"처럼 보이지만, 실제로는 페이지당
  20건 × 3개 소스 테이블 서브쿼리가 될 위험이 있었음 — 어드바이저가 "성능 결정을 UI 결정처럼 숨기지 말라"고 지적. 메인 목록
  쿼리(`/api/dpf/search`)는 건드리지 않고, 현재 페이지에 보이는 vehicle_id만 모아 별도 배치 조회 API 1개
  (`GET /api/dpf/service-records/derived-stats`)를 새로 부른다. PostgREST에 GROUP BY가 없어서 집계는 서버 응용 코드(JS)에서 한다.
- **컬럼 예산**: `DpfVehicleTable`가 이미 19컬럼·`minWidth 1780px`이라 6개를 그대로 더하면 25개가 된다 — 크린어스도 부착현황에서
  일부 컬럼(주소, 이전업체명)을 뺐던 것으로 관찰됨(§2.1). 기존 19개 컬럼은 그대로 두되(담당자가 실제 쓰는지 확인 없이 임의로
  빼지 않음), 신규는 3개(접수현황=최근접수일/마지막처리일 2줄 스택, 처리횟수=`크N·ASN·철N` 압축, 부착경과일)+액션버튼 1개 =
  4개만 추가(23컬럼, minWidth ~2150px)로 압축.
- **철부횟수 벤더 처리**: `dpf_device_installations`가 엠즈 차량에는 애초에 안 채워진다는 걸 git log(103ec33, "엠즈 형식 임포트
  지원") 커밋 메시지와 `ALL_TABS`의 `installation`/`inspection`/`subsidy` 탭이 전부 `vendors: ['fujino']`로 제한된 것으로
  교차 확인 — 엠즈는 자체 DB 파일을 가져와 차량 마스터만 채우고 설치이력 서브테이블은 임포트하지 않는다. 그래서 API는 벤더를
  따로 안 걸러도 엠즈 차량은 항상 0이 돌아오지만, "실제 철거 0회"와 "애초에 추적 안 함"을 화면에서 구분하려고 **클라이언트에서만**
  `vendor==='mz'`이면 `-`로 덮어쓰기로 결정. 이 판단은 DB에 직접 접속해 확인한 게 아니라 커밋 이력 교차검증으로 내린 것이라,
  구현 중 실제 엠즈 차량 1대로 브라우저 검증할 때(체크리스트) 다시 한번 눈으로 확인한다.
- **재조회 패턴**: 2단계 사후검토에서 `/dpf/service/page.tsx`의 통계 `useEffect`가 `[result.total]`에 걸려 필터 바뀔 때마다
  전역 통계를 다시 도는 걸 지적받았음(§2단계 사후 검토). 3단계 신규 코드에서 같은 실수를 반복하지 않기 위해, 파생통계 fetch를
  별도 `useEffect`로 만들지 않고 `search()` 콜백 안에서 목록 fetch 직후 바로 호출하도록 명시적으로 결정.
- **버튼→모달**: `ServiceRecordFormModal`은 1단계에서 이미 `initialCategory?: DpfServiceCategory`를 받아서 수정 불필요.
  "접수" 버튼은 `initialCategory` 생략(폼 드롭다운에서 직접 선택), "물류" 버튼은 `'parts_delivery'`로 프리셋(폼 안에서
  `urea`로 바꿀 수 있음) — 크린어스의 "접수상담"/"엔진물류" 두 버튼과 같은 구분이지만, 우리는 폼을 하나로 통합했으므로
  차이는 초기 선택값뿐이다(별도 스트립다운 폼 없음).
- `DpfVehicleTable`는 `app/dpf/page.tsx` 한 곳에서만 쓰임을 그렙으로 확인 — 액션 버튼을 prop으로 게이팅할 필요 없음.

## 3단계 계획 4차 검토 (2026-09-11, 어드바이저) — 3차 검토 후 4가지 추가 반영
1. **취소 건이 횟수에 섞이면 안 됨**: `clean_count`/`as_count`를 처음엔 `status` 무관하게 셌는데, 2단계 접수현황 요약 바가
   `cancelled`를 대기/완료 집계에서 빼는 것과 숫자가 어긋나면 담당자가 혼란스러워한다는 지적 — `status != 'cancelled'`만
   세도록 §7 수정. `last_reception_date`는 취소 건도 포함(접수 자체는 실제 발생).
2. **로딩 중간 상태를 0으로 보여주면 안 됨**: 목록 fetch와 파생통계 fetch가 순차라서 `derivedStats[id]===undefined`인
   구간이 항상 생김 — "기록 없음(API가 준 0)"과 "아직 안 옴(undefined)"을 구분해서 후자는 `…`로 표시하기로 결정.
3. **"부착경과일" 라벨이 실제로는 구변일 기반**: `installation_date`가 `lib/dpf-column-map.ts`에서 "구변일자/구조변경일자"에
   매핑됨을 확인(그렙으로 검증, DB 직접 조회 아님) — 크린어스의 "부착경과일"은 물리적 부착일이라는 별개 개념이고 우리
   스키마엔 없으므로, 같은 이름을 쓰지 않고 "구조변경경과일"로 명명 변경.
4. **컬럼 레이아웃 재검토**: "접수현황" 2줄 스택 컬럼은 그 행만 키가 달라져 세로 정렬이 깨지므로 포기하고 최근접수일/
   마지막처리일을 단일 라인 별도 컬럼 2개로 분리 — 결과적으로 신규 컬럼이 3개가 아니라 4개(최근접수일/마지막처리일/
   처리횟수/구조변경경과일)+액션버튼 1개 = 24컬럼(23→24로 수정).

## 3단계 구현/검증 결과 (2026-09-11)
설계 그대로 구현, 브라우저 검증에서 재설계가 필요한 문제는 없었음.
- 배치 조회 API를 테이블에 붙이기 전에 `javascript_tool` fetch로 단독 호출해 응답 모양부터 확인(2단계와 동일 절차) —
  테스트 차량 3건(크리닝 완료 1건 + AS 진행중 1건 + 크리닝 취소 1건)을 만들어 넣고 정확히 `clean_count=1(취소 제외)`,
  `last_reception_date`=취소 건 포함 최댓값, `last_processed_date`=취소 건 포함 최댓값으로 나오는 것을 API 레벨에서 먼저 검증.

  크리닝 1회차 완료)과 목록 파생값(크2·AS1·철0, 최근접수일 2026-09-11, 마지막처리일 2026-09-09)이 정확히 일치함을 확인 —
  집계 로직이 실제 데이터로도 설계 의도대로 맞아떨어짐.
- 엠즈 차량(KL2UL61FDYP002208)에서 최근접수일/마지막처리일이 `—`(기록 없음), 철부횟수가 `-`(벤더상 미추적) — 각각 다른
  이유의 대시(dash)이지만 화면상 구분은 없음. 담당자가 실제로 헷갈려하면 후속으로 툴팁 등을 고려할 수 있으나, 지금은
