# 컨텍스트 노트 — 업무단계 키 불일치 (2026-09-09)

## 현상
보조금(5년경과) 업무가 칸반에서 "[보조금]확인필요" 칸에 표시됨. DB status는 바뀌지 않았고(이력 0건) 표시 문제.

## 원인
- 보조금(id 2)과 보조금(5년경과)(id 10)의 task_stages가 같은 라벨에 다른 stage_key를 씀.
  - "[보조금]승인(착공신청서제출필요)": `custom_1777968825327`(보조금) vs `custom_1778198486933`(5년경과)
  - "[보조금]설치완료(준공도서 작성 필요)": `subsidy_pre_completion_document_submit`(보조금) vs `subsidy_installation`(5년경과)
  - "[보조금]진행불가": `custom_1778201843963`(보조금) vs `custom_1778201850667`(5년경과)
- 반대로 같은 키가 카테고리마다 다른 라벨인 경우도 있음: `subsidy_installation`은 동시진행에서 "설치완료".
- 커밋 1dad1f2(2026-09-07) 이전엔 subsidy 타입 전부가 보조금 메인 단계로 표시돼 5년경과 업무에 메인 키가 저장됐고, 이후 자기 카테고리 키로 대조하면서 고아가 됨. 고아는 첫 칸(확인필요)에 배치되는 로직.

## 결정
- 데이터: 사용자가 22건 치환 SQL 직접 실행(2026-09-09). business_id NULL인 유신단열(주) 1공장 1건은 별도 UPDATE 필요.
- 표시: status 키가 자기 카테고리에 없으면 라벨로 같은 카테고리 키를 찾는 resolver를 클라이언트에 둠. task.status 원본은 건드리지 않음(다음 드래그가 올바른 키를 씀).
- resolver는 키가 여러 라벨을 가질 수 있으므로 같은 task_type 카테고리 우선으로 모든 라벨을 후보로 시도.
- 재발 방지: 단계 추가 API가 키 미지정 시 같은 task_type 카테고리의 같은 라벨 키를 재사용. 대상 카테고리에 이미 그 키가 있으면(라벨 다름) custom_ 키로 폴백해 409 방지.
- 수정 모달에서 사업장 재선택/진행구분 변경 시 무조건 첫 단계로 초기화하던 것을 라벨 기준 이관으로 변경(1dad1f2가 만든 잠재 버그 제거).

## 검증 중 추가 발견
- 복수 진행구분(전체) 칸반은 칸을 라벨로 합치는데 grouped는 status 키로 저장해, 같은 키가 다른 라벨을 갖는 카테고리(예: subsidy_approval_pending = "[보조금]보조금 승인대기(접수완료)" vs 동시진행 "보조금 승인대기")끼리 덮어써 업무가 사라지고 폴백으로 확인필요 칸에 들어갔다. grouped 키를 라벨로 바꿔 해결.
- 복수 보기에서 드롭하면 칸의 키가 다른 카테고리 키일 수 있어 handleDrop에서 resolveStageKey로 업무 카테고리 키로 맞춘다.

## 미수정(후속)
- 사업장 progress_status 변경(사업장 수정 모달, 재분류 SQL) 시 업무 status 키를 서버에서 같이 이관하지 않음. 라이브 시스템 영향 범위가 커서 별도 작업으로 분리.
- TaskMobileModal 내부의 현재 단계 하이라이트(`task.status === step.status`)는 미적용.
